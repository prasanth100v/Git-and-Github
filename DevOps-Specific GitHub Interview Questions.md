## 🎯 Branch protection rules - DevOps Interview Answer
  * Branch protection rules in GitHub are used to secure critical branches like `main` or `production` by enforcing `pull requests`, `code reviews`, `CI/CD status checks`, and `restricting direct pushes`.
  * They help `maintain code quality`, `security`, and `stable deployments` in DevOps workflows.

| 🔢 Rule | 🎯 Feature                         | 🧠 What It Does                              | ✅ Benefit                                     | 💡 Example                           |
| ------- | ---------------------------------- | -------------------------------------------- | --------------------------------------------- | ------------------------------------ |
| 🟦 1    | 🔍 Require PR Reviews              | Developers must get approvals before merging | Improves code quality            | Require `2 approvals`                |
| 🟩 2    | ⚙️ Require Status Checks           | CI/CD pipelines must pass before merge       | Prevents broken code from reaching production | Jenkins / GitHub Actions / SonarQube |
| 🟨 3    | 🚫 Restrict Direct Pushes          | Blocks direct push to protected branches     | Enforces controlled workflow                  | `feature → PR → review → merge`      |
| 🟪 4    | 📈 Require Linear History          | Prevents merge commits                       | Keeps Git history clean & readable            | Allow only `rebase` or `squash`      |
| 🟥 5    | 🔒 Prevent Force Push              | Blocks `git push --force`                    | Protects commit history                       | Avoid accidental overwrite           |
| 🟧 6    | 🛡 Prevent Branch Deletion         | Prevents deleting critical branches          | Protects production branches                  | `main`, `release`, `production`      |

   * Git squash = Git squash `combines multiple commits` into a `single commit` to simplify and clean up project history
